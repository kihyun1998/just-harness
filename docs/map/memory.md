# Project memory

How the REPL carries instructions and the model's own notes from one session to the next (`src/memory.rs`, `ToolContext::allow` in `src/tools/mod.rs`, `system_prompt` and the turn start in `src/main.rs`). It follows Claude Code, the project's target ([thegraph](../agents/thegraph.md)), read raw from code.claude.com/docs `memory.md` and `prompt-caching.md` on 2026-10-29.

## The project context message

At the start of a new session, and again right after a compaction ([compaction](compaction.md)), the REPL adds one user message, `<project-context>`, before the user's line: the instruction files, each under its path, then the first part of the memory index. It is written to the session file like any message, so a resumed session sends exactly what it sent before and does not read the files again; edits to them take effect in a new session or after the next compaction, as in Claude Code ("Editing CLAUDE.md mid-session": read once at session start and held; reloaded on `/clear`, `/compact` or restart). Nothing is added when there are no files and the index is empty.

The issue asked for the instructions in the system prompt; Claude Code delivers CLAUDE.md "as a user message after the system prompt, not as part of the system prompt itself" (memory page), and so does this. In the system prompt, a file edited between sessions would change `system`, and every thinking block of a resumed session would then fail its check ([tool-result-clearing](tool-result-clearing.md); #12). As a message, the edit only reaches a new or compacted history, which no thinking predates. After a compaction the message comes after the summary, so it is read from disk then and sent as new. Claude Code orders project context before the conversation, so its compacted request reads unchanged instruction files from the cache; maintainer's call (2026-10-29) to keep the summary first, since matching it would change the session format again for a cache read of the instruction files and the index alone.

## Which files

Maintainer's calls (2026-10-29): both `CLAUDE.md` and `AGENTS.md` are read, chosen by `instructionFiles` in `~/.just-harness/settings.json` with Claude Code's three values for its "Project instructions" setting (shown against a command-line flag and against both); the user's own files live in `~/.just-harness/`.

- `claude-md-or-agents-md` (the default): a folder's `CLAUDE.md`, `.claude/CLAUDE.md` and `CLAUDE.local.md`, or its `AGENTS.md` and `.claude/AGENTS.md` when it has none of those three.
- `claude-md-and-agents-md`: both, the `CLAUDE.md` files first.
- `claude-md`: the `CLAUDE.md` files only.

The rule applies to `~/.just-harness/` (`CLAUDE.md`, `AGENTS.md`) and then to the working folder, so the user's files come first and the project's are read last, as Claude Code orders from broadest to most specific. Each file is read only when its real path, symlinks followed, stays inside the folder it was found in (`~/.just-harness/` or the working folder) and is not a `.env` file; the same holds for `MEMORY.md` in the memory folder. Without that, a committed `CLAUDE.md` linking to `~/.ssh/id_ed25519` or to `.env` would put that file in the first request and the session file without anyone being asked, past the file tools' confinement ([agent-loop](agent-loop.md)); review found it. Claude Code asks before an import from outside the project; this has no imports, so it refuses. A file reached under two names, an `AGENTS.md` linked to `CLAUDE.md` in `claude-md-and-agents-md`, is read once, as Claude Code does. A file over 4 MiB is skipped, Claude Code's limit, and so is one that cannot be read, without losing the others. The REPL prints `[loaded <path>]` for each file read and `[not loaded <path>: <why>]` for each left out, as Claude Code shows which instruction files loaded. An unknown `instructionFiles` value, or a settings file that is not JSON, stops the REPL at start with the reason; a missing file means the defaults. Claude Code reads that setting only from user-level settings, not from a project's; this has no project settings at all, so a repository cannot change which files are read.

## Memory

Maintainer's call (2026-10-29, shown against the API's memory tool `memory_20250818` and against instructions only): memory is kept the Claude Code way. Each project has `~/.just-harness/projects/<project with / as ->/memory/`, created at start with mode 0700, where the project is the git repository the working folder is in (`project_root`: the nearest folder above with a `.git` folder, or for a worktree's `.git` file the main repository its `commondir` names), and the working folder itself outside a repository. That is Claude Code's rule ("derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory", memory page); maintainer's call (2026-10-29, shown against keeping one memory per working folder and against leaving it to an issue). Checked against a real `git worktree add` on 2026-10-29: the worktree and a subfolder of the main repository resolved to the main repository. Two projects whose paths differ only in `/` against `-` share one folder name, as sessions do ([sessions](sessions.md)); memory has no meta to tell them apart. If the folder cannot be created, the REPL says so and runs without memory (no folder allowed, no memory paragraph in the system prompt), rather than not starting. The system prompt tells the model what to keep there (the user's role and preferences, confirmed corrections with why, ongoing work, where outside information lives; not what the code, its history or the instruction files say), one fact per file with a line per file in `MEMORY.md`. The first 200 lines of `MEMORY.md`, cut at 25,000 bytes, go into the project context message, Claude Code's limits; the other files are read when the model wants them.

The model reads and writes memory with `read_file` and `edit_file` by absolute path: `ToolContext::allow` adds the memory folder to where the file tools may go, beside the working folder ([agent-loop](agent-loop.md), folder confinement). `.env` files stay refused there too. Writing memory asks for approval like any edit; Claude Code writes its memory folder without asking, which this does not copy.

The API's memory tool was the alternative: the model is trained on it, but the API then adds "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" to the system prompt (memory tool page, 2026-10-29), so each task starts with a tool call, and whether Ollama accepts the tool type was not known.

Checked on 2026-10-29 against a local fake API: the first request carried the user's `CLAUDE.md`, the project's `AGENTS.md` and the index in that order, the system prompt named the memory folder, an `edit_file` into the memory folder was asked and wrote the file; after a compaction the context came after the summary with the `AGENTS.md` edited since; a resume after a further edit sent the recorded context unchanged. `main.rs` has no automated test of this.
