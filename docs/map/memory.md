# Project memory

How the REPL carries instructions and the model's own notes from one session to the next (`src/memory.rs`, `ToolContext::allow` in `src/tools/mod.rs`, `system_prompt` and the turn start in `src/main.rs`). It follows Claude Code, the project's target ([thegraph](../agents/thegraph.md)), read raw from code.claude.com/docs `memory.md` and `prompt-caching.md` on 2026-10-29.

## The project context message

At the start of a new session, and again right after a compaction ([compaction](compaction.md)), the REPL adds one user message, `<project-context>`, before the user's line: the instruction files, each under its path, then the first part of the memory index. It is written to the session file like any message, so a resumed session sends that message as it was. Nothing is added when there are no files and the index is empty.

### When a session resumes

A resumed session reads the files at its first turn and compares them with the copies in its last `context` record ([sessions](sessions.md)), path by path. What differs goes in one `<project-context-update>` user message before the user's line: each changed file under its path, then `Instructions no longer present:` and the paths gone. When nothing differs nothing is sent, and a resume in the same state adds no message. With no earlier files, the files come as a `<project-context>` instead: the update's wording speaks of earlier copies and of instructions carried above, and there are none, so a session started in a folder with no instruction files would otherwise never be told to follow them; a review pass reproduced that. Files are compared as they are carried, with no blank end, and a blank file is carried by nothing, so a change only in trailing space is no change and emptying a file reads as no longer present. A running session does not read them again before a compaction.

That is what Claude Code does, measured and not from its docs, which describe `/cd` and "reloaded on `/clear`, `/compact` or restart". Claude Code 2.1.318 in `-p` mode against a local fake API, with its config folder in a scratch folder (2026-11-05): a resume with nothing changed added no message; an edited project or user `CLAUDE.md` or a new `MEMORY.md` came back in a block beginning "Instruction files were re-read when this session started; these differ from their earlier copies — each replaces its earlier copy, and the instructions preamble above still applies"; a deleted file gave "Instructions no longer present: <path>"; a second resume repeated nothing; and the same text at another path counted as a change, with the old path no longer present. A folder move also gets a system-role "# Environment update" message, for which this keeps `<working-folder>` as a user message ([sessions](sessions.md)). Maintainer's call (2026-11-05, shown against only a resume in another folder): every resume.

A review pass reported further measurements, not repeated here: Claude Code does the same in interactive mode; it sends the whole format with its preamble when no instructions came before; a file over 4 MiB or unreadable reads as no longer present, as here; trailing space and an emptied file behave as here. Where it differs: it adds a warning when `MEMORY.md` is past its limits, so an edit beyond them is still sent, where here it is no change; in interactive mode a file edited while running arrives on the next line as "changed on disk since you last read it", where here it waits (no live watching).

A known hole: when the memory folder changes while the working folder does not, as a `git init` above it does, the model hears that the old `MEMORY.md` is no longer present and is not told the new folder; the recorded system prompt names the old one, whose writes are refused, until the next compaction. Reproduced against a local fake API on 2026-11-05; the refusal was read from the code. Maintainer's call (2026-11-05): recorded here, not filed. A review pass reported that Claude Code does not name the new folder either; not repeated here.

## Which files

Maintainer's calls (2026-10-29): both `CLAUDE.md` and `AGENTS.md` are read, chosen by `instructionFiles` in `~/.just-harness/settings.json` with Claude Code's three values for its "Project instructions" setting (shown against a command-line flag and against both); the user's own files live in `~/.just-harness/`.

- `claude-md-or-agents-md` (the default): each folder's `CLAUDE.md`, `.claude/CLAUDE.md` and `CLAUDE.local.md`, or every folder's `AGENTS.md` and `.claude/AGENTS.md` when none of those three carries anything.
- `claude-md-and-agents-md`: both, each folder's `CLAUDE.md` files first.
- `claude-md`: the `CLAUDE.md` files only.

The folders are `~/.just-harness/`, by the same rule with only `CLAUDE.md` and `AGENTS.md` and on its own for the choice between them, then every folder from the filesystem's top down to the working folder, so the user's files come first and the working folder's last, as Claude Code orders from broadest to most specific. A folder below the working folder is not read. The working folder is its real path, so the folders above it are those of the real path, as Claude Code's are.

This follows Claude Code as measured: 2.1.318 in `-p` mode against a local fake API on 2026-11-05 read top down in that order within each folder; with a `CLAUDE.md` above and an `AGENTS.md` in the working folder only the `CLAUDE.md`, and the other way round likewise; with only `AGENTS.md` files all of them; a `CLAUDE.md` above the git repository too; and through a linked working folder the real path's parents. The memory page states the choice across folders ("in your working directory or any directory above it"). Maintainer's calls (2026-11-05): no stop at the git repository, shown against stopping there, with the cost that a file at `/tmp/CLAUDE.md` or `~/CLAUDE.md` is read; and the choice across folders, shown as a change from choosing folder by folder, so an `AGENTS.md` in a subfolder is no longer read under a `CLAUDE.md` above.

A file counts for that choice only when it would be carried: a blank file, one over the size limit, one that cannot be read and one refused for a link do not count, so a `touch ~/CLAUDE.md` or a link planted in `/tmp` does not silently drop a project's `AGENTS.md`. Claude Code does the same for the first three, as a review pass measured; it follows the link, so for it that file does count. Not counting the refused link is a judgement of this change, reported to the maintainer.

The home folder is a folder like any other, except that its `.claude/` is left out and does not count for that choice, whether reached from the home folder or as a folder above the working folder, through a link too. It holds Claude Code's own user file, which Claude Code reads first as its user file (measured the same way), and this harness's user files are in `~/.just-harness/`. Reading it would bring in Claude Code's instructions only when running under the home folder. Maintainer's calls (2026-11-05): not read from the home folder, shown against reading it; and not read when running inside it either, shown against Claude Code's reading it there, as a review pass measured. Another folder's `.claude/` is read, and so are the folders below `~/.claude`.

In a worktree inside its repository's main checkout, the folders from that checkout's top down to the worktree give only `CLAUDE.local.md`: their `CLAUDE.md`, `.claude/CLAUDE.md` and `AGENTS.md` belong to another checkout of the same files, and do not count, while `CLAUDE.local.md` does. A review pass found this in Claude Code, and it was reproduced against real worktrees (2026-11-05): `r/wt` read `r/CLAUDE.local.md` and `r/wt/CLAUDE.md` and not `r/CLAUDE.md`, `r/.claude/CLAUDE.md` or `r/AGENTS.md`, while the folders above `r` were read as usual, and so was `b` for a worktree `b/main` beside a bare `b/repo.git`, which has no checkout. A worktree beside its repository reads only its own folders above. A nested repository or a submodule has a `.git` that is not a worktree's, so nothing is skipped; the review pass measured those as the same.

Each file is read only when its real path, symlinks followed, stays inside the folder it was found in (`~/.just-harness/`, the folder above, or the working folder) and is not a `.env` file; the same holds for `MEMORY.md` in the memory folder. Without that, a committed `CLAUDE.md` linking to `~/.ssh/id_ed25519` or to `.env` would put that file in the first request and the session file without anyone being asked, past the file tools' confinement ([agent-loop](agent-loop.md)); review found it. Claude Code follows such a link: measured the same way, a `CLAUDE.md` above linking out of its folder sent the target, and one linking to `.env` sent `SECRET=1`. This departs from it on purpose. Claude Code asks before an import from outside the project; this has no imports, so it refuses. Maintainer's call (2026-11-05, shown against allowing links in the folders above, which would drop the defence for a committed link at a repository's top when running in a subfolder). The wider the folder, the less this holds: a review pass measured `~/CLAUDE.md` linking to `~/.ssh/id` going into the request and the session file, and at `/` nothing is outside. Maintainer's call (2026-11-05, shown against refusing every link in the home folder and at `/`, which would stop a dotfiles-managed `~/CLAUDE.md` from being read): the rule stays, since planting one takes write access to that folder. A file reached under two names, an `AGENTS.md` linked to `CLAUDE.md` in `claude-md-and-agents-md`, is read once, as Claude Code does. A file over 4 MiB is skipped, Claude Code's limit, and so is one that cannot be read, without losing the others. The REPL prints `[loaded <path>]` for each file read and `[not loaded <path>: <why>]` for each left out, as Claude Code shows which instruction files loaded; on a resume, `[loaded <path>]` only for the files that differ, and `[no longer present <path>]`. An unknown `instructionFiles` value, or a settings file that is not JSON, stops the REPL at start with the reason; a missing file means the defaults. Claude Code reads that setting only from user-level settings, not from a project's; this has no project settings at all, so a repository cannot change which files are read.

## Memory

Maintainer's call (2026-10-29, shown against the API's memory tool `memory_20250818` and against instructions only): memory is kept the Claude Code way. Each project has `~/.just-harness/projects/<project with / as ->/memory/`, created at start with mode 0700, where the project is the git repository the working folder is in (`project_root`: the nearest folder above with a `.git` folder, or for a worktree's `.git` file the main repository its `commondir` names), and the working folder itself outside a repository. That is Claude Code's rule ("derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory", memory page); maintainer's call (2026-10-29, shown against keeping one memory per working folder and against leaving it to an issue). Checked against a real `git worktree add` on 2026-10-29: the worktree and a subfolder of the main repository resolved to the main repository. Two projects whose paths differ only in `/` against `-` share one folder name, as sessions do ([sessions](sessions.md)); memory has no meta to tell them apart. If the folder cannot be created, the REPL says so and runs without memory (no folder allowed, no memory paragraph in the system prompt), rather than not starting. The system prompt tells the model what to keep there (the user's role and preferences, confirmed corrections with why, ongoing work, where outside information lives; not what the code, its history or the instruction files say), one fact per file with a line per file in `MEMORY.md`. The first 200 lines of `MEMORY.md`, cut at 25,000 bytes, go into the project context message, Claude Code's limits; the other files are read when the model wants them.

The model reads and writes memory with `read_file` and `edit_file` by absolute path: `ToolContext::allow` adds the memory folder to where the file tools may go, beside the working folder ([agent-loop](agent-loop.md), folder confinement). `.env` files stay refused there too. Writing memory asks for approval like any edit; Claude Code writes its memory folder without asking, which this does not copy.

The API's memory tool was the alternative: the model is trained on it, but the API then adds "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" to the system prompt (memory tool page, 2026-10-29), so each task starts with a tool call, and whether Ollama accepts the tool type was not known.

Checked on 2026-10-29 against a local fake API: the first request carried the user's `CLAUDE.md`, the project's `AGENTS.md` and the index in that order, the system prompt named the memory folder, an `edit_file` into the memory folder was asked and wrote the file; after a compaction the context came after the summary with the `AGENTS.md` edited since. `main.rs` has no automated test of this.

Checked on 2026-11-05 against a local fake API, running the same sequence as the Claude Code measurement above: a resume with nothing changed sent only the line and wrote no `context` record; an edited project or user file, a deletion, a new memory index, and resumes in two other folders each sent what differed, once, with the old folder's file no longer present; a compaction sent the whole context, and a resume after it nothing. From a folder with no instruction files, a resume in one with `AGENTS.md` sent `<project-context>`; a change only in trailing space sent nothing; emptying it sent no longer present, and filling it again `<project-context>`. With the home folder above a repository: a new session in a subfolder carried the user's file, `~/CLAUDE.md` and the repository's `CLAUDE.md`, and neither `~/.claude/CLAUDE.md` nor the subfolder's `AGENTS.md`; a `CLAUDE.local.md` linking out of the repository printed `[not loaded]`; resuming in the repository and back in the subfolder sent only `<working-folder>`; deleting the repository's file sent no longer present. Real worktrees, a blank file above and the inside of `~/.claude` read what this note says.
