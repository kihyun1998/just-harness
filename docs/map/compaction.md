# Compaction

How the REPL replaces a long conversation with a summary the model writes, and continues from that summary with the project context and recent files read again from disk (`src/compaction.rs`, `Agent::send` in `src/agent.rs`, the turn start in `src/main.rs`, the `compact` record in `src/session.rs`). The API's server-side compaction is not used: the project implements it itself (#8, #11).

## The shape: simple compaction

After a compaction the history is one user message, `SUMMARY_PREFIX` and the summary, then the project context read again from disk ([memory](memory.md)), then the recent files read again from disk ([below](#putting-recent-files-back)), and the user's next line follows (two user messages in a row are accepted, [agent-loop](agent-loop.md)). Nothing from before is replayed, so no thinking block is sent after a history it was not produced from ([tool-result-clearing](tool-result-clearing.md)), and no request can fail that check. The preserved-thinking page (platform.claude.com/docs/en/build-with-claude/preserved-thinking, "Compact on the client", read raw on 2026-10-29) recommends this shape and says Claude models are trained on long-horizon tasks with it. Keeping the last turns verbatim (keep-tail) would need their thinking stripped or the `drop_block` beta, because that thinking was produced against the history the summary replaced.

Prior art, read from source: codex sends the history with its compaction prompt as the next user turn and keeps the user's own recent messages, up to 20,000 tokens, with the summary (`codex-rs/core/src/compact.rs`, prompt in `codex-rs/prompts/templates/compact/prompt.md`); goose summarizes in a separate call with its own system prompt and keeps the last user message (`crates/goose/src/context_mgmt/mod.rs`). `SUMMARY_REQUEST` takes codex's list of what a handoff summary holds. Claude Code (code.claude.com/docs context-window and prompt-caching pages, read raw on 2026-10-29) sends its summary request the same way, with the conversation's system prompt, tools and history ending in a summarization instruction, and keeps only the summary of the messages; after it, it puts back from disk CLAUDE.md, memory, up to five recently read or edited files (a file over 5,000 tokens as a path only) and invoked skills, and it stops compacting automatically after a few attempts when the context refills at once.

Maintainer's call (2026-10-29, shown with codex keeping the user's own messages up to 20,000 tokens, goose keeping the last one, and Claude Code's reloading of files): the summary alone, with the user's new line after it; recent files and the stop came later (#13), and CLAUDE.md belongs to project memory (#9).

## The summary request

`summary_request` is the history unchanged with `SUMMARY_REQUEST` appended as a user message, sent by `Agent::send` with the same model, `max_tokens`, system, tools, extra fields and cache markers as a turn's requests, as one request whose tool calls are not run. Because everything before the appended message is the request the last turn ended with, it reads that prefix from the cache, and the thinking in it is still valid. A separate call with its own system prompt, as goose makes, would read nothing from the cache.

`tool_choice` is not set to forbid tools, although the request asks for no tool calls: the prompt-caching page says a change to `tool_choice` invalidates the cached messages, so the request would write the whole conversation to the cache again. The summary is the reply's text blocks joined (`summary`), and only from a reply that stopped at `end_turn` or `max_tokens`. A reply that stopped at a tool call or a refusal is not a summary even when it holds text: a sentence like "Let me check the log first." before a tool call would otherwise replace the whole conversation, for good, since the session file replays it; review found it. A reply with no summary, or a failed request, leaves the conversation whole and says so, and the next turn tries again: one more request of the whole conversation each turn, mostly read from the cache, until one succeeds or the attempts run out ([below](#when-it-stops)). A summary cut at `max_tokens` is used and reported; `SUMMARY_REQUEST` asks for what remains to be done second, so a cut takes the record of what was done before it takes the next step.

## When it compacts

At the start of a user turn, before clearing ([tool-result-clearing](tool-result-clearing.md)) and before the user's line is added, when the last request of the last turn kept had a prompt and reply of `trigger_tokens` or more (`Usage::history_tokens`): the reply is in the history the next request sends, its thinking included, since Claude Haiku 5.5 keeps every earlier turn's thinking (thinking page, "Keep all prior turns"). Counting the prompt alone left the reply out, which lens found. A compaction makes clearing that turn moot. The docs say not to compact between a `tool_use` and its result; at a turn start the summary request comes after every result, so a history ending in results the model has not answered (the iteration cap, `q`) is summarized with them. One long turn is not compacted while it runs.

Maintainer's call (2026-10-29, shown against counting with `POST /v1/messages/count_tokens` before every turn, which the issue named, and against counting only after a resume): the trigger is the last kept request's usage. `count_tokens` is free with a rate limit of its own (token-counting page, 2026-10-29) and Ollama's compatibility page lists it as not supported. The cost: the size of the line the user is about to send is not known, and the first turn after a resume has no usage, so it does not compact.

`CompactPolicy::default()` triggers at 90,000 tokens. The prompt-caching page prices Claude Haiku 5.5 prompts over 100,000 tokens five times higher, and its context window is 1,000,000 tokens (model overview page), so the price step, not the window, sets the ceiling. 90,000 leaves 10,000 tokens for the next line and the turn's own growth before that step; that margin is a judgement, not a measurement. Clearing triggers lower, at 80,000, so it gets the first chance to keep the prompt down.

## When it stops

`CompactGuard` counts attempts in a row that made no room. An attempt that gave no summary counts. An attempt that gave one counts unless the first request after it had a prompt below the trigger, which starts the count over; Ctrl-C does not count. A turn ending below the trigger also starts the count over, which is how clearing can bring a stopped session back. A turn with no usage (a failed or cancelled one, or the first after a resume) leaves the count alone. A refusal for size starts a compaction whatever the count, and counts as an attempt ([below](#when-a-request-is-refused-for-its-size)). After `max_attempts`, 3, the turn that would attempt again prints one error instead; the user's line is still sent and clearing keeps running.

Claude Code documents only the refill: "automatic compaction succeeded but a file or tool output immediately refilled the context window several times in a row", and it "stops retrying to avoid wasting API calls on a loop that isn't making progress" (troubleshooting page, read raw on 2026-11-05). Neither of its pages gives a number, so 3 is a judgement, not a measurement. Here neither case loops by itself: each costs one more request of the whole conversation per line the user sends. A line can see two compactions, when the one at its start fails and the line is then refused, and at most about 8 requests.

The first request is the test because a turn may grow past the trigger on its own after a summary that made plenty of room: counting how the turn ended stopped compaction in a healthy session whose turns ran from 30,000 to 95,000 tokens, which lens reproduced against a fake API. So a session of long turns keeps paying one summary request per line. What can fill the first request is the summary (up to `max_tokens`), the instruction files, the memory index and the recent files; `<recent-files>` is text, so clearing does not reduce it.

Maintainer's calls (2026-11-05): count both cases in one number, shown against the refill alone and the failed summary alone. Refill means the first request after the summary, shown against how the next turn ends, with the 30,000-to-95,000 case. Send the user's line after the stop, shown against refusing it. The cost of sending it is that the prompt keeps growing, and past 100,000 tokens each request is priced five times higher ([above](#when-it-compacts)); the error says so. Two of Claude Code's four recovery steps are `/compact` and `/clear`, which do not exist here, so the error names what does: a turn ending below the trigger, and quitting and resuming, which starts the count over since it is kept only in memory.

## When a request is refused for its size

"If the input alone already exceeds the model's context window, the API returns a 400 `invalid_request_error` ("prompt is too long") on every model" (context-windows page, read raw on 2026-11-05), and over 128 MB a 413 `request_too_large` (errors page). `ApiError::is_prompt_too_long` tells those apart, by the words of that message, case aside; the real wording was not probed, since a request that size takes paid calls. Another wording stays an ordinary error.

A refused request has no usage, so nothing would ever start a compaction, a resume included. So the refusal itself starts one, whatever the attempt count says. The history as it stands would be refused again, so the summary request is shrunk (`shrunk_summary_request`): without the messages read again or told again after a compaction (`<project-context>`, `<project-context-update>`, `<recent-files>`, `<working-folder>`), every tool result cleared, and no thinking, since removing messages invalidates all of it ([tool-result-clearing](tool-result-clearing.md)). When that is refused too, each further attempt keeps about half as much, the newest, from a user's request on so that no tool call loses its result, under a `LEFT_OUT` message; 5 attempts at most, a judgement. The REPL says when it starts leaving messages out; what was cut is not in the summary, and the oldest message may be an earlier summary. A reply with no summary, such as one stopped by `model_context_window_exceeded` (context-windows page: input within the window is accepted, and generation stops at its limit) or a tool call, moves to the next attempt too, and so does a 400 of any kind, which covers the unprobed case below.

When every attempt fails, or nothing can be cut, as when the bulk is in the newest exchange, the last resort is `LEFT_OUT` and the summary request alone: the conversation is lost from the history, and the REPL says so; the session file keeps every original message. A review pass measured Claude Code recovering this way from a single exchange, and with several exchanges failing and refusing the next line too; not repeated here. Maintainer's call (2026-11-05, shown against using it only for one exchange, and against not using it, either of which leaves a session stuck): always, since a stuck session was the issue.

Not probed: whether the API accepts a history with every thinking block removed when it ends in tool results not yet answered (the iteration cap, `q`). The preserved-thinking page calls removing all of them valid and the errors page says filtering them from the latest assistant message gives a 400, and [tool-result-clearing](tool-result-clearing.md) avoids this case. A probe was approved on 2026-11-05 and not run: the key in `.env` got `401 invalid x-api-key` (`req_011Cgj3JnMUKQwPgay5Bkx3n`). If it is refused, that session reaches the last resort.

Then the line is sent again, once, with no error shown when the compaction succeeds. Claude Code does the same: 2.1.318 in `-p` mode against a local fake API refusing past a size (2026-11-05) sent a small summary request with the older part replaced by a marker, then the line with the summary. A review pass reported that it continues a turn whose tools ran, with their results in the summary; here that turn is dropped before the summary, so the summary does not hold its work.

Because the instruction files leave the summary request and are read from disk after it, a file that made every request fail stops mattering once it is fixed. That was #19. Against a local fake API on 2026-11-05: a session resumed with a 40,000-byte `CLAUDE.md` against a 30,000-byte limit compacted and then said it was still too long; a further resume did the same, with one more summary request per line; and after the file was fixed the next line compacted, read the small file and went through, and the next resume was healthy.

The exits, none of which says why it was too long, since the error's token counts are not read:
- **A refusal after a tool ran.** The line is not sent again, since an edit could run twice; the turn is dropped as any failed turn is, the compaction still runs, and whichever exit follows says not to send the line as it was. Maintainer's call (2026-11-05, shown against never resending and against not cutting old messages). It can be wrong on the safe side: a `pause_turn` or calls that were all denied count as tools having run.
- **Still too long right after a compaction.** Said, with whether the line was sent. The next line starts over.
- **Nothing to summarize.** Only carried messages, or none, are left. They are dropped from the history (the `drop` clears the copies, [sessions](sessions.md)), the requests switch to this build's prompt as after a compaction, the REPL says so, and the next line reads the files again.
- **Compaction failed or was cancelled.** Said, with whether the line was sent.

Checked against the same fake API on 2026-11-05: a conversation growing past the limit, a summary request refused until halved, a new session with only a huge instruction file or with a line too large by itself, a reply pushing one exchange over the limit (last resort, and the next lines went through), a refusal after a `read_file`, and a summary request answered with another 400 reaching the last resort, each as above, and `--continue` after a compaction sent what was sent. `main.rs` has no automated test of this (#18).

## Putting recent files back

Right after a compaction, and only then, `put_back` brings back up to five of the files `read_file` and `edit_file` succeeded on in the session, most recently modified first (the file's modification time on disk), read from disk now, as one `<recent-files>` user message after the project context. A file over 5,000 tokens comes back as its path without its contents. That follows Claude Code (context-window page, read raw on 2026-11-05: "re-reads up to five of the files Claude has read or edited in the session, choosing the ones modified most recently. A file over 5,000 tokens comes back as a path reference without its content"). Whether "modified most recently" means the file's time on disk is not stated there; the time on disk is this project's reading. An image or a PDF does not come back and takes no place among the five: measured on Claude Code 2.1.319 in one process against a local fake API (2026-11-07), a text file came back and a small image and a small PDF did not; large ones there were not measured. A notebook comes back as its cells with its images, except an image the API refused earlier in the session, which would be refused again, as the same measurement showed, the images as blocks after the message's text, so `is_carried` goes by a message's first block. Over 5,000 tokens by its file's size, images included, it comes back as its path. A file with a binary extension does not come back either, whatever it holds, since `read_file` refuses it. Files changed only through `shell` are not tracked, as the page names only reads and edits, and a call that was refused or denied does not count. Maintainer's call (2026-11-05, shown against leaving this out and shipping the stop alone).

Sizes are estimated at 4 bytes per token, because `count_tokens` was left out (see [When it compacts](#when-it-compacts)); a file of many short tokens can be over the limit in fact and still come back whole. By that estimate this adds up to about 25,000 tokens, below the 90,000 trigger by itself; there is no cap on it together with the summary and the project context. A file's lines are not cut as `read_file` cuts them.

Each path goes through `ToolContext::resolve_file` again, so the working-folder confinement and the `.env` refusal hold now as they did for the call, whatever the path has become since. A file that is gone, is not a regular file (`read_to_string` on a FIFO would block), is refused, is an image, a PDF or of a binary extension, or is neither UTF-8 text nor a readable notebook at or under the limit takes no place among the five; the size is checked before reading, so a large file of another kind, such as a binary with no extension, comes back as its path. A file the project context of the same compaction carries takes no place either, so `MEMORY.md`, which the model is told to edit, does not crowd out code or go twice; maintainer's call (2026-11-05), since Claude Code's docs do not cover this. The part of `MEMORY.md` past the index limits does not come back. Files are compared by their real paths. A relative path is kept joined to the folder the call ran in, so a session moved to another folder does not bring back a same-named file from there; the first folder's files are refused as outside the new one.

`TouchedFiles` is not recorded on its own: `load` rebuilds it from every `message` record in the file, including those a compaction or a `drop` removed from the history, since a call with a recorded result in a dropped turn did run. Results are appended when a reply's whole round of calls has finished, so an edit in a round cut by Ctrl-C has no result and is not tracked. The put-back message is an ordinary `message` record, so a resume sends what was sent, and `FORMAT_VERSION` does not change.

## On disk

The session file keeps every original message and adds `{"type":"compact","summary":<text>}`; `load` replaces the history with `compacted(summary)` at that point, and later `drop` and `clear` records count from the compacted history ([sessions](sessions.md)). As with `clear`, what `compacted` builds is part of the format: changing `SUMMARY_PREFIX` would change what a resumed session sends, which costs a cache write but fails no check, since nothing before the summary carries thinking.

## The report

The summary streams to the terminal like a reply, followed by `[compacted into a summary of N bytes]` and the request's token line. After a compaction the requests switch to this build's system prompt and tool definitions, which are recorded again ([sessions](sessions.md)); the summary request itself still carries the session's recorded ones, so it reads the cache. The REPL then forgets the last cached request whatever the outcome: after a compaction the prompt starts over, and after a failed one the next request does not extend the summary request, so comparing against it would report a changed prefix that did not change. Ctrl-C during the summary request cancels it and the line typed, and nothing is recorded.

Checked on 2026-10-29 against a local fake API: a summary request answered with a tool call kept the conversation and wrote no record; after a turn reporting a 95,000-token prompt, the next line first sent the summary request, whose messages began with the previous request's and whose tools, system, cache markers, model and `max_tokens` were identical; the turn's request then held the summary message and the new line; `--continue` afterwards sent the same two messages first. A summary request answered with a 400 left the conversation whole and wrote no `compact` record. The REPL side is `compact` in `src/main.rs`, which has no automated test (#18).

Checked on 2026-11-05 against a local fake API, running the binary:
- **Refill:** with every request reporting 95,000 input tokens, three lines started a summary request, the next printed the error, and the one after neither; a 1,000-token turn then re-armed it, and the next large turn compacted again.
- **Long turns:** with each turn's first request at 30,000 tokens and its last at 95,000, six lines gave five compactions and no error.
- **Failed summary:** a 400 on every summary request gave three requests and the error, and so did a reply stopping at a tool call.
- **Put back:** after reading `a.txt`, `b.txt`, `CLAUDE.md` and a refused `.env`, the request after a compaction held the summary, the project context, `<recent-files>`, then the line; `--continue` sent those messages unchanged, and a compaction after that resume put back `b.txt` then `a.txt` and neither `CLAUDE.md` nor `.env`.
- **No compaction:** a session whose only turn was dropped, resumed with an empty history, sent the line with no `<recent-files>`.

- **An edit:** an approved `edit_file` that created `new.txt` came back in `<recent-files>` after a compaction; an edit stopped at the prompt did not.

## Known holes

- **A crash right after the `compact` record.** `needs_files` lives in memory, so a process that dies before the next message is written resumes without the recent files, until the next compaction. The window is the synchronous code between the two writes; its length was not measured. Maintainer's call (2026-11-05): recorded here, not filed; a fix would change the session format. The project context does come back: with a `compact` record added to a session file by hand, `--continue` sends the summary, a `<project-context>` with every file, and the line ([sessions](sessions.md)).

## Not built

No manual `/compact` command, no compaction inside a turn, no keeping the last turns verbatim, no `count_tokens`, no invoked-skill or hook re-injection (this harness has neither), no saved attempt count, and nothing for Ollama.
