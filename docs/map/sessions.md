# Sessions on disk

How a conversation is kept as a file and resumed (`src/session.rs`, `src/main.rs` `open_session` and `Log`), and why. Prior art read from source: codex's rollout recorder (`codex-rs/rollout/src/recorder.rs`: one `.jsonl` per session, a `SessionMeta` first line, file creation deferred until there is something to write, unparsable lines warned about and skipped on load; `list.rs` filters sessions by the `cwd` in their meta) and Claude Code's own session files (`~/.claude/projects/<folder>/<uuid>.jsonl`, one typed record per line, the file mode 0600 and `~/.claude/projects` 0700, measured on this machine on 2026-10-29 under umask 022).

## The file

`~/.just-harness/sessions/<working folder with each / as ->/<id>.jsonl`, created with the first message, not at start, so starting and quitting leaves no empty session for `--continue` to pick (lens reproduced that). The first line is the `SessionMeta` (`version`, `id`, `created` in Unix seconds, `cwd`, `model`) tagged `"type":"session"`. Each later line is a `message` record, written and synced to the disk (`sync_data`) as the message is added, a `drop`, `clear`, `compact`, `prompt` or `cwd` record. The id is the creation second and 8 random hex digits (`new_id`). The file is mode 0600 and the folders the harness creates 0700, as Claude Code does, since the conversation holds every tool output, an approved `cat .env` included.

`--continue` takes the most recently modified session in the folder whose meta names this working folder; the slug alone is not unique (`/x/y` and `/x-y` share one), which lens reproduced. A session file of a newer `version` than `FORMAT_VERSION` is refused rather than read with its unknown records skipped.

Maintainer's calls (2026-10-29, each shown with its alternatives): the folder-per-working-folder layout under the home folder, not codex's `YYYY/MM/DD` and not a `.just-harness/` inside the project (where a conversation full of tool output could be committed); `--continue` and `--resume <id|path>`, not `--resume` alone.

## Why each record exists

- **`drop`.** The REPL removes a turn from the history on an API error or Ctrl-C (see [agent-loop](agent-loop.md)). Appending messages alone would bring that turn back on resume, so the REPL writes `{"type":"drop","keep":n}` and `load` cuts the history back to `n`.
- **`clear`.** The REPL clears old tool results between turns ([tool-result-clearing](tool-result-clearing.md)). The file keeps the original messages and writes `{"type":"clear","before":n}`; `load` applies the same clear at that point, so a resumed session sends what it sent before. A thinking block is valid only after the exact history it was produced from, so resuming the uncleared history, or a clear recomputed differently, would fail the next request. `FORMAT_VERSION` is 2 since this record, so a build that knows only 1 refuses a file this build created rather than skipping the record. A file created as version 1 keeps that version when this build resumes it and may then gain `clear` records; an older build would skip them and resume the uncleared history, whose next request fails. Left so: no other build of this format is in use.
- **`compact`.** The REPL can replace the history with a summary ([compaction](compaction.md)). The file keeps the original messages and writes `{"type":"compact","summary":<text>}`; `load` replaces the history with the summary message there, and the `drop` and `clear` records after it count from that history. `FORMAT_VERSION` is 3 since this record. As with `clear`, a file created at an older version keeps it when resumed and may gain `compact` records, which an older build would skip, then apply the later `drop` and `clear` counts to the whole history; left so for the same reason.
- **`prompt`.** The system prompt and tool definitions the requests carry, written right after the meta line when the file is created and again after every compaction. Resuming sends the last one recorded until the next compaction, then this build's, as Claude Code does ("builds the system prompt once, on a conversation's first request ... and records it in the session. Until the conversation is compacted, every later request uses that recorded prompt, including after you return to the conversation with `--resume` or `--continue`", cli-reference page, read raw on 2026-10-29). A thinking block is valid only behind the `system` and `tools` it was produced with: on 2026-10-29 the `tool-loop` conversation resent with one sentence added to its system prompt got a 400 naming the `system` prompt (`req_011CgW15ks36TTDVwz9RYyMS`) and with the recorded one a 200 (`req_011CgW15okBT4x2VREp9MrbX`). A file with no readable `prompt` record, from before `FORMAT_VERSION` 4, resumes on this build's prompt with a warning and records it. If it holds thinking from a different system prompt, as every session saved before the memory paragraph was added does, each request fails until the thinking is removed; nothing here removes it. When this was built (2026-10-29) no session file existed on the development machine (`~/.just-harness` was absent), so rebuilding the old prompt for such files, which lens proposed, was left out. Tool calls still run through this build's tools, whatever definitions were sent. A version-4 file read by an older build loses only the `prompt` records, which it skips.

The trap: `api::Tool` is part of the format now. A field added to it must be optional when read, or every recorded `prompt` line fails to parse, is skipped, and the session resumes as if it had none.

Checked on 2026-10-29 against a local fake API: a new session's file had the `prompt` record right after the meta line; with its system text edited in the file, `--continue` and the summary request of the compaction after it sent the edited text, the turn after the compaction sent this build's and recorded it; a file with the `prompt` lines removed resumed with the warning and gained a record. `main.rs` has no automated test of this.
- **`cwd`.** The working folder the session runs in from that line on. A session resumed in a folder other than the one it last ran in (the last `cwd` record, else the meta's) gets one user message at the start of its next turn, `<working-folder>`, naming the new folder and this run's memory folder or saying there is none, and then a `cwd` record, so resuming again in the same folder adds no second message. The recorded system prompt is not changed: the preserved-thinking page says to put changing context in the newest turn rather than edit the prefix ("Put changing context in the newest turn"). Maintainer's call (2026-10-29, shown against Claude Code's session picker, which hands back a `cd` into the session's own folder and resumes elsewhere only when that folder is gone; how Claude Code tells the model of a move was not found in its docs). `FORMAT_VERSION` is 5 since this record; an older build skips `cwd` lines as unreadable, which only means a repeated message. The message is written before the record: a crash between the two gives a second message on the next resume, the other order could give none. The message comes before the turn's own line, so a failed or cancelled first turn keeps it. Finding a moved session still goes by the meta's folder: `--continue` and `--resume <id>` from the new folder look only in its own session folder, so a moved session is reached there with `--resume <path>`, and `--continue` in the old folder can pick a session that has moved away. Checked on 2026-10-29 against a local fake API: a session started in A and resumed in B carried one such message, resumed in B again still one, resumed back in A a second one naming A. `main.rs` has no automated test of this; the `cwd` record has one in `tests/session.rs`.
- **The repair.** A process that ends between an assistant `tool_use` and its results leaves a call with no answer, and the API refuses the next request with a 400 (probed in #2, [agent-loop](agent-loop.md)). `load` answers each such call at the end of the history with `No result: the session ended before this call's result was recorded, so it may or may not have run.` (the call may have run before the process ended) and returns it as `repair`; resuming appends it to the file, so it happens once.
- **The cut.** A call inside the history with no result in the next message (a result line that did not parse) is not repairable in place, so `load` cuts the history at that assistant message and reports `cut_at`; resuming records it as a drop.
- **Cut lines.** A crash mid-write leaves a last line with no line end. `load` skips any line that does not parse and counts it (the REPL says how many), as codex does. `SessionLog::open` writes a line end first when the file does not end with one; without it the first message after resuming was glued to the cut line and lost too, which the fake-API check showed and `appending_after_a_cut_last_line_starts_a_new_line` pins.
- **A failed write** stops all writing to that file for the rest of the session, and the REPL says so; continuing would leave a gap that a later resume reads as a broken history, and a `drop` count that no longer matches the file.

## What is not in the file

The `a` allow-for-the-session answers (see [agent-loop](agent-loop.md), Approval) start empty on resume, so a resumed session asks again. A session resumed from another working folder runs its tools in the new one; the REPL warns when `cwd` differs. Its recorded system prompt and project context still name the first folder and its memory folder; the `<working-folder>` message above tells the model where the file tools now work ([memory](memory.md)). The new folder's instruction files and memory index are not read. Paths, ids and errors read from a session file are printed through `printable`.

## How messages reach the file

`run_turn` appends through one function, `append` in `src/agent.rs`, which calls `Observer::on_message` after each message lands in the history; the REPL's observer writes it. The REPL writes the user's own line itself.

Checked on 2026-10-29 against a local fake API with `HOME` in a scratch folder: start and quit (no file), `--continue` with nothing saved, a new session then `--continue` (the next request carried the earlier messages; file 0600, folders 0700), a cancelled turn (dropped, not restored), and `--resume <path>` on a file ending in a cut line after an unanswered call (skipped, warned, answered, next request valid). `main.rs` has no automated test; neither does `sync_data`, nor `latest` skipping an entry whose metadata cannot be read.

No listing of sessions, no cleanup of old ones, no locking against two processes writing one file.
